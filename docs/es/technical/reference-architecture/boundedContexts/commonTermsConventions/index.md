# Términos y convenciones habituales utilizados

El equipo de arquitectura de referencia ha utilizado términos y convenciones comunes a lo largo de todo el proceso de diseño y documentación del modelo de arquitectura de referencia Mojaloop 2.0.<br/><br/> Le rogamos que utilice esta lista para familiarizarse con cualquier término que le resulte desconocido o que haya olvidado. La lista incluye referencias a artículos y documentos de terceros que figuran en la sección «Lecturas recomendadas» de este documento.

|    **Convención/Término**    |       **Descripción**       |
| :------------------------ | :-------------------------- |
| **Actores**                                                            | Participante en un caso de uso: persona o sistema externo. Todos los casos de uso están impulsados por actores. |
| **a. C.**                                                                | Contexto delimitado: Un contexto delimitado es un componente del desarrollo orientado al diseño (Design-Driven Development) y suele contener uno o varios subdominios. Los contextos delimitados son entidades del Espacio de Soluciones y contienen una única solución aplicable a uno o varios subdominios. <br/> <br/> (*Para obtener más información, consulte: [DDD Inspired Architecture Overview](../../introduction/#ddd-inspired-architecture-overview) en la descripción general del Espacio de Soluciones, o nuestra sección [Lecturas recomendadas: artículos y documentos de referencia](../../furtherReading/#reference-articles-and-documents)*) |
| **UC** | Caso de uso: Un caso de uso es una lista de acciones o pasos que describen las interacciones entre un actor (persona o sistema externo) y un sistema para alcanzar un objetivo concreto. Un ejemplo de caso de uso de Mojaloop es «Realizar una transferencia con confirmación del Beneficiario».<br/><br/> (*Para obtener más información, consulte el artículo de Wikipedia «Caso de uso» en la sección [Lecturas recomendadas: Artículos y documentos de referencia](../../furtherReading/#reference-articles-and-documents) de este documento*) |
| **Sincronización**                                                              | Comunicaciones síncronas, unidireccionales o bidireccionales, que forman parte del proceso de origen. Se representa mediante una línea continua en los esquemas de UC. Se utiliza habitualmente para mensajes que deben incluirse en un flujo de trabajo concreto de UC a fin de que este se ejecute correctamente. Un ejemplo de mensajería sincrónica es una consulta del BC de transferencias al BC de gestión del ciclo de vida de los participantes para obtener los datos de los participantes, en caso de que no estén almacenados en Caché, con el fin de completar una solicitud de transferencia. |
| **Asíncrono**                                                             | Comunicaciones asíncronas, unidireccionales o bidireccionales, que no forman parte del proceso de origen. Se representan mediante una línea punteada en los esquemas de UC. Se suelen utilizar para «eventos», que sirven para indicar algo que ha ocurrido, que es inmutable y que no va a cambiar; por ejemplo, los informes de devolución de llamada. |
| **PUBLICACIÓN**                                                              | Se utiliza para crear nuevos recursos. En concreto, se emplea para crear recursos subordinados. Es decir, subordinados a algún otro recurso (por ejemplo, el recurso principal). En otras palabras, al crear un nuevo recurso, se envía una solicitud POST al recurso principal y el servicio se encarga de asociar el nuevo recurso con el principal, asignándole un ID (URI para el nuevo recurso), etc. Si la creación se realiza correctamente, el Sistema devolverá un encabezado «Location» con un enlace al recurso recién creado, con el estado 201 HTTP.<br/><br/>(*Para obtener más información, consulte el «Restful API Tutor», cuya referencia figura en la sección [Lecturas complementarias: Artículos y documentos de referencia](../../furtherReading/#reference-articles-and-documents) de este documento*) |
| **OBTENER**                                                               | Se utiliza para leer (o recuperar) una representación de un recurso. En el caso «normal» (sin errores), el método GET devuelve una representación en XML o el valor JSON, así como un código de respuesta HTTP de 200 (OK). En caso de error, suele devolver un 404 (NOT FOUND) o un 400 (BAD REQUEST).<br/><br/>(*Para obtener más información, consulte el «Restful API Tutor», cuya referencia figura en la sección [Lecturas complementarias: Artículos y documentos de referencia](../../furtherReading/#reference-articles-and-documents) de este documento*) |
| **PONER**                                                               | Se utiliza para realizar actualizaciones: se envía una solicitud PUT a un recurso conocido URI, cuyo cuerpo de solicitud contiene la representación recién actualizada del recurso original. En algunos casos, el método PUT también puede utilizarse para crear nuevos recursos; sin embargo, debido a su complejidad, no se recomienda (en su lugar, se debe utilizar el método POST).<br/><br/>(*Para obtener más información, consulte el «Restful API Tutor», cuya referencia figura en la sección [Lecturas complementarias: Artículos y documentos de referencia](../../furtherReading/#reference-articles-and-documents) de este documento*) |
| **200 (OK)**                                                          | HTTP: Código de estado que indica «Éxito». La solicitud se ha realizado correctamente. Por lo general, la información que se devuelve junto con el código de estado depende del método utilizado en la solicitud. Por ejemplo, en Mojaloop, los métodos más utilizados son POST, GET y PUT. En el caso de POST, la respuesta describiría o incluiría el resultado de la acción; en el caso de GET, la entidad solicitada se envía en la respuesta; y en el caso de una solicitud PUT, la respuesta sería similar a la de una solicitud POST.<br/><br/>(*Para obtener más información, consulte el «Restful API Tutor», cuya referencia figura en la sección [Lecturas complementarias: Artículos y documentos de referencia](../../furtherReading/#reference-articles-and-documents) de este documento*) |
| **201 (Creado)**                                                     | HTTP: Código de estado que indica «Creado» o «Fulfilment». Esto significa que la solicitud se ha satisfecho y que se puede acceder al nuevo recurso a través del URI devuelto en la respuesta de la entidad. El servidor de origen creará el recurso antes de devolver un código 201 y, si no puede hacerlo de inmediato, devolverá un 202 (Aceptado) en su lugar.<br/><br/>(*Para obtener más información, consulte el «Restful API Tutor», referencia del documento que figura en la sección [Lecturas complementarias: Artículos y documentos de referencia](../../furtherReading/#reference-articles-and-documents) de este documento*) |
| **202 (Aceptado)**                                                    | HTTP: Código de estado que indica que se ha aceptado una solicitud para su tramitación, pero que aún no se ha completado. Es posible que la solicitud se tramite o no cuando el Sistema lo permita, ya que podría ser rechazada durante el proceso de tramitación. Dado que la operación es asíncrona, tampoco existe la posibilidad de reenviar el código de estado, independientemente del resultado. La respuesta 202 es deliberadamente no vinculante para permitir que una solicitud se procese sin que el Agente tenga que permanecer conectado hasta que ello ocurra. La respuesta debe incluir una indicación del estado del sistema y, bien un enlace a una plataforma de Monitoreo, bien una indicación de cuándo se tramitará la solicitud.<br/><br> (*Para obtener más información, consulte el «Restful API Tutor», cuya referencia figura en la sección [Lecturas complementarias: Artículos y documentos de referencia](../../furtherReading/#reference-articles-and-documents) de este documento*) |
| **Seguridad y salud en el trabajo**                                                               | Servicio de host abierto: Describe la documentación de los métodos que deben emplearse para integrar con éxito los sistemas de fase posterior en un sistema de fase previa ya existente, sin que sea necesario realizar modificaciones en la plataforma de fase previa. Por lo general, se ofrece compatibilidad con múltiples tipos de clientes, sin que se preste especial atención a ningún cliente concreto. Se exigirá que el sistema posterior comprenda la documentación publicada por el sistema anterior. Los sistemas anteriores suelen combinar el OHS y el PL. systems.<br/><br/> Actualmente se utiliza en las siguientes entidades: FSPIOP External API; ISO External API; Notificaciones & Alertas BC; PISP ML External API; PISP ISO External API; Scheduling BC; Transferencias & Transacciones BC; Acuerdo (Cotización) BC; Cuentas y Saldos BC; Liquidaciones BC; Gestión del ciclo de vida de los participantes; Búsqueda de cuenta y descubrimiento de cuenta BC)<br/><br/>(*Para obtener más información, consulte el artículo «Strategic Domain-Driven Design», cuya referencia figura en la sección [Lecturas complementarias: Artículos y documentos de referencia](../../furtherReading/#reference-articles-and-documents) de este documento*) |
| **PL**                                                                | Lenguaje publicado: Se describe como el pariente más cercano del servicio de host abierto y, a menudo, se utiliza junto con él. El lenguaje publicado utiliza un lenguaje documentado —por ejemplo, XML— para las operaciones básicas de E/S con el sistema para el que se está utilizando. No se requiere ninguna biblioteca ni especificación de implementación concreta para conectarse al sistema, siempre que se cumpla con el lenguaje publicado. No es necesario ejecutar únicamente servicios web con un lenguaje publicado. También se pueden realizar acciones como cargar un archivo en una carpeta concreta, lo que a su vez desencadena una operación que almacena el contenido del archivo en una ubicación especificada por la aplicación.location.<br/>location.<br/> Actualmente se utiliza en las siguientes entidades: FSPIOP Externo API; ISO Externo API<br/><br/>(*Para obtener más información, consulte el artículo «Strategic Domain-Driven Design», cuya referencia figura en la sección [Lecturas recomendadas: Artículos y documentos de referencia](../../furtherReading/#reference-articles-and-documents) de este documento*)) |
