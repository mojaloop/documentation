# Avaliação de Saúde GET

Discussão sobre o projeto para a nova implementação do Health Check.


## Objetivos

O objetivo deste projeto é implementar uma nova verificação de estado para os serviços do Mojaloop Switch que permita um maior nível de detalhe.

Características:
- Limpar os estados «HTTP» (não é necessário analisar a resposta para saber que não existem problemas)
- ~Compatibilidade retroativa com as verificações de integridade existentes~ - Já não é um requisito. Consulte [esta discussão](https://github.com/mojaloop/project/issues/796#issuecomment-498350828).
- Informações sobre a versão do API e há quanto tempo está em execução
- Informações sobre as ligações dos sub-serviços (Kafka, sidecar de registo e MySQL)

## Formato do pedido
`/health`

Utiliza a verificação de integridade recentemente implementada. Tal como discutido [aqui](https://github.com/mojaloop/project/issues/796#issuecomment-498350828), uma vez que não haverá sobrecarga adicional na ligação (por exemplo, enviar um ping a uma base de dados) no âmbito da implementação da verificação de integridade, não há necessidade de complicar as coisas com uma versão simples e detalhada.

Códigos de resposta:
- `200` - Sucesso. O API está em funcionamento e está ligado com sucesso aos serviços necessários.
- `502` - Erro de gateway. O API está em funcionamento, mas o API não consegue estabelecer ligação ao serviço necessário (por exemplo, `kafka`).
- `503` - Serviço indisponível. Esta resposta não está implementada neste projeto, mas será a resposta por predefinição caso a API não esteja em funcionamento

## Formato da resposta

| Nome  | Tipo | Descrição | Exemplo |
| --- | --- | --- | --- |
| `status`        | `statusEnum`                       | O estado do serviço. As opções são `OK` e `DOWN`. _Consulte o ponto `statusEnum` abaixo_. | `"OK"`   | 
| `uptime`        | `number`                           | Há quanto tempo (em segundos) que o serviço está ativo.  | `123456`                     |
| `started`       | `string` (data e hora no formato ISO) | Quando o serviço foi iniciado (UTC)                     | `"2019-05-31T05:09:25.409Z"` | 
| `versionNumber` | `string` (semver)                  | A versão atual do serviço.                    | `"5.2.5"`                    |
| `services`      | `Array<serviceHealth>`             | Uma lista dos serviços dos quais este serviço depende e o respetivo estado de ligação | _ver abaixo_ |

### serviceHealth

| Nome  | Tipo | Descrição | Exemplo |
| --- | --- | --- | --- |
| `name`    | `subServiceEnum`   | O nome do subserviço. _Consulte o ponto `subServiceEnum` abaixo_.       | `"broker"` | 
| `status`  | `enum`             | O estado do serviço. As opções são `OK` e `DOWN`    | `"OK"`     | 

### subServiceEnum

A enumeração `subServiceEnum` descreve o nome de um subserviço:

Opções:
- `datastore` -> A base de dados para este serviço (normalmente uma base de dados MySQL).
- `broker`    -> O mediador de mensagens para este serviço (normalmente Kafka).
- `sidecar`   -> O subserviço sidecar de registo ao qual este serviço está associado.
- `cache`     -> O sub-serviço de cache ao qual este serviço está associado.


### statusEnum

A enumeração de estado representa o estado do sistema ou do subserviço.

Existem duas opções:
- `OK`    -> O serviço ou subserviço está em bom estado.
- `DOWN`  -> O serviço ou subserviço não está em bom estado.

Quando um serviço apresenta o valor `OK`: o API é considerado em bom estado e todos os subserviços são igualmente considerados em bom estado.

Se qualquer sub-serviço tiver o valor `DOWN`, toda a verificação de integridade falhará e o valor API será considerado `DOWN`.

## Definição do estado de funcionamento de um sub-serviço

Não basta simplesmente executar um comando «ping» num subserviço para saber se este está a funcionar corretamente; pretendemos ir um passo além. Estes critérios irão variar consoante cada subserviço.

### `datastore`

Para o valor `datastore`, um estado de `OK` significa:
- Existe uma ligação à base de dados
- A base de dados não está vazia (contém mais de uma tabela)


### `broker`

Para o valor `broker`, um estado de `OK` significa:
- Existe uma ligação ao broker do Kafka
- Os tópicos necessários existem. Isto irá variar consoante o serviço para o qual a verificação de integridade está a ser executada.

Por exemplo, para que o serviço «`central-ledger`» seja considerado em bom estado, é necessário que sejam encontrados os seguintes tópicos:
```
topic-admin-transfer
topic-transfer-prepare
topic-transfer-position
topic-transfer-fulfil
```

### `sidecar`

Para o valor `sidecar`, um estado de `OK` significa:
- Existe uma ligação ao sidecar


### `cache`

Para o valor `cache`, um estado de `OK` significa:
- Uma ligação existente ao cache

### Exemplos de pedidos e respostas:

__Verificação de estado do sistema «Legacy» concluída com sucesso:__

```bash
GET /health HTTP/1.1
Content-Type: application/json

200 SUCCESS
{
  "status": "OK"
}
```


__Nova verificação de estado de saúde bem-sucedida:__

```
GET /health?detailed=true HTTP/1.1
Content-Type: application/json

200 SUCCESS
{
  "status": "OK",
  "uptime": 0,
  "started": "2019-05-31T05:09:25.409Z",
  "versionNumber": "5.2.3",
  "services": [
    {
      "name": "broker",
      "status": "OK",
    }
  ]
}
```

__Verificação de integridade falhada, mas o API está ativo:__

```
GET /health?detailed=true HTTP/1.1
Content-Type: application/json

502 BAD GATEWAY
{
  "status": "DOWN",
  "uptime": 0,
  "started": "2019-05-31T05:09:25.409Z",
  "versionNumber": "5.2.3",
  "services": [
    {
      "name": "broker",
      "status": "DOWN",
    }
  ]
}
```

__Verificação de integridade falhada:__

```
GET /health?detailed=true HTTP/1.1
Content-Type: application/json

503 SERVICE UNAVAILABLE
```
