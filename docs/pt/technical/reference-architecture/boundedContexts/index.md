# Contexto Delimitado

Nesta secção, analisamos em pormenor cada um dos Contextos Delimitados identificados, indicando a sua finalidade (descrição), os subdomínios abrangidos, os casos de uso a que cada Contexto Delimitado se refere e as observações finais, sempre que estas tenham sido incluídas.

| Atores                                                            | Participante de um caso de uso, seja ele humano ou um sistema externo. Todos os casos de uso são orientados por atores. |

Um exemplo de caso de uso do Mojaloop é «Efetuar transferência com confirmação do beneficiário».<br/><br/> (*Leitura complementar: «Caso de uso» (Definição) — Da Wikipédia, a enciclopédia livre*) |

Ou seja, subordinados a algum outro recurso (por exemplo, o recurso pai). Por outras palavras, ao criar um novo recurso, efetue um pedido POST ao recurso pai e o serviço encarregar-se-á de associar o novo recurso ao recurso pai, atribuindo-lhe um ID (novo recurso URI), etc. Se a criação for bem-sucedida, o sistema devolverá um cabeçalho «Location» com um link para o recurso recém-criado, com o estado 201 HTTP.<br/><br/>(*Fonte: Restful API Tutor - consulte Referências e leituras complementares*) |

Em caso de erro, na maioria das vezes devolve um código de resposta 404 (NÃO ENCONTRADO) ou 400 (PEDIDO INVÁLIDO).<br/><br/> (*Fonte: Restful API Tutor - ver Referências e leituras complementares*) |
| PUT                                                               | Utilizado para funções de atualização, a realização de um pedido PUT para um recurso conhecido URI, com o corpo do pedido a conter a representação recém-atualizada do recurso original. | 200 (OK)                                                          | HTTP Código de estado que indica «Sucesso». O pedido foi bem-sucedido. Normalmente, a informação devolvida com o código de estado depende do método utilizado no pedido. Por exemplo, no Mojaloop, os métodos mais frequentemente utilizados são POST, GET e PUT. No caso do POST, a resposta descreveria ou incluiria o resultado da ação; no caso do GET, a entidade solicitada é enviada na resposta; e, no caso de uma solicitação PUT, a resposta seria semelhante à de uma solicitação POST. <br/> <br/> (*Fonte: Restful API Tutor - ver Referências e leituras complementares*) |
| 201 (Criado)                                                     | HTTP Código de estado que indica «Criado» ou «Atendido». Isto significa que o pedido foi atendido e que o novo recurso está acessível através do URI devolvido na resposta da entidade. O servidor de origem criará o recurso antes de devolver um código 201 e, caso não consiga fazê-lo imediatamente, devolverá, em vez disso, um 202 (Aceite).<br/><br/> (*Fonte: Restful API Tutor - ver Referências e leituras complementares*) |
| 202 (Aceito)                                                    | HTTP Código de estado que indica que um pedido foi aceite para processamento, mas ainda não foi concluído. O pedido poderá ou não ser processado quando o sistema o permitir, uma vez que poderá ser rejeitado durante o processamento. Como a operação é assíncrona, também não existe a possibilidade de reenviar o código de estado, independentemente do resultado. A resposta 202 é deliberadamente evasiva, para permitir que uma solicitação seja processada sem exigir que o agente permaneça ligado até que tal ocorra. A resposta deve incluir uma indicação do estado do sistema e, ou um indicador para uma plataforma de monitorização, ou uma indicação de quando a solicitação será processada.<br/><br> (*Fonte: Restful API Tutor - ver Referências e leituras complementares*) |

Normalmente, é permitido o apoio a vários tipos de clientes, não havendo qualquer foco específico em clientes concretos. O sistema a jusante deverá compreender a documentação publicada pelo sistema a montante. | PL                                                                | Linguagem Publicada: Descrita como a mais próxima do serviço de anfitrião aberto e frequentemente utilizada em conjunto com este. A LP utiliza uma linguagem documentada, por exemplo, XML, para operações básicas de E/S no sistema para o qual está a ser utilizada. Não é necessária qualquer biblioteca específica nem especificação de implementação para a ligação ao sistema, desde que se cumpra a linguagem publicada. Não é necessário executar apenas serviços web com uma Linguagem Publicada. Também é possível, por exemplo, carregar um ficheiro para uma pasta específica, o que, por sua vez, desencadeia uma operação que armazena o conteúdo do ficheiro num local especificado pela aplicação.<br/><br/>Atualmente utilizada nas seguintes entidades: FSPIOP Externa API; ISO Externa API<br/><br/> (*Fonte: Strategic Domain-Driven Design - ver Referências e leituras complementares*) |
