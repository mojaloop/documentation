# Ferramentas e tecnologias

Aqui documentamos o raciocínio por trás de certas escolhas de ferramentas, tecnologia e processos para o Mojaloop. Incluímos também os links/versões recomendados para cada uma destas ferramentas.

**ESCOLHAS DE FERRAMENTAS**

* **Desenvolvimento de APIs**
  * O **Open API 3.0 ** é aproveitado para o desenvolvimento de APIs (anteriormente Swagger 2.0).
  * O ** ISTIO** como API Gateway (o WSO2 está agora desatualizado a partir do Mojaloop v16.0.0 - Congo e do IaC v5.0.0) oferece uma plataforma empresarial para integrar APIs, aplicações e web services — localmente e através da Internet. Fornece também ao Mojaloop uma camada de segurança e um portal de desenvolvimento.
* **Circle-CI** - Esta ferramenta é usada para a construção contínua e o deployment contínuo. Precisávamos de um sistema online de construção e teste contínuos capaz de funcionar com muitos projetos pequenos e uma equipa distribuída. O Jenkins foi considerado, mas exige alojar um servidor e muita configuração. O CircleCI permitiu uma solução sem host, que podia ser iniciada sem custos e com configuração muito limitada. Pensámos que poderíamos começar com o CircleCI e mudar mais tarde, caso o ultrapassássemos, mas isso não foi necessário.
* **Dactyl** – Precisamos de poder imprimir a documentação online. Embora seja possível imprimir ficheiros markdown diretamente, um a um, gostaríamos de reunir os ficheiros num conjunto de documentos PDF finais, nos quais uma página poderá acabar em mais do que um manual final. O [Dactyl](https://github.com/ripple/dactyl) é uma ferramenta de conversão open source mantida que converte entre markdown e PDF. Inicialmente tentámos o Pandoc, mas tinha bugs na conversão de tabelas. O Dactyl corrige isso e é muito mais flexível.
* **DBeaver** - O [DBeaver](https://dbeaver.io/) é uma ferramenta de base de dados multiplataforma e gratuita para desenvolvedores, programadores de SQL, administradores de bases de dados e analistas. Suporta todas as bases de dados populares: MySQL, PostgreSQL, MariaDB, SQLite, Oracle, DB2, SQL Server, Sybase, MS Access, Teradata, Firebird, Derby, etc.
* **Docker** - O motor de contentores Docker cria e corre o contentor Docker a partir do ficheiro de imagem Docker.
* O **Docker hub** é usado para ligar, construir, testar e enviar os repositórios de código do Mojaloop. Precisávamos de suportar a execução tanto local como na cloud. Temos muitos microserviços pequenos com configurações e requisitos específicos muito simples. A forma mais fácil de garantir que o serviço funciona do mesmo modo em todos os ambientes, do desenvolvimento local, à cloud, até à produção alojada, é colocar cada microserviço num contentor Docker juntamente com todos os pré-requisitos de que necessita para correr. O contentor passa a ser uma unidade segura, fechada, pré-configurada e executável.
* **Draw.io** – Precisamos de criar imagens para os nossos documentos e diagramas de arquitetura usando uma ferramenta \(idealmente gratuita\) amigável para open source, que seja agnóstica quanto à plataforma, suporte formatos vetoriais e raster, permita desenho WYSIWYG, funcione com markdown e seja fácil de usar. Analisámos muitas ferramentas, incluindo: Visio, Mermaid, PlantUML, Sketchboard.io, LucidChart, Cacoo, Archi e Google Drawings. O Draw.io pontuou no topo para as nossas necessidades. É gratuito, mantido, fácil de usar, produz os nossos formatos, integra-se com o DropBox e o GitHub, e é agnóstico quanto à plataforma. Para guardar os nossos diagramas, temos de guardar duas cópias — uma em formato SVG \(vetorial escalável\) e a outra em PNG \(raster\). Usamos o formato PNG nos documentos, dado que pode ser visualizado diretamente no GitHub. O SVG é usado como cópia mestra, por ser editável.
* **ESLint** - No código JavaScript, usamos o [ESLint](https://eslint.org/) como guia de estilo de código e ferramenta de imposição de estilo.
* **GitHub** – O [GitHub](https://github.com/Mojaloop) é um serviço de repositório de código-fonte amplamente utilizado, baseado em git, o sistema padrão de controlo de versões de código-fonte para projetos open source. Por isso, a decisão de usar o GitHub foi simples. Criamos sempre uma story para o trabalho de integração. Criamos bugs para quaisquer problemas. Garantimos que todas as stories são acompanhadas ao longo do pipeline, para assegurar métricas fiáveis.
* **Helm** - O gestor de pacotes Helm para Kubernetes fornece deployments e configurações templatizados e permite a gestão da complexidade global.
* **IaC** - Infrastructure as Code (IaC) é o conjunto de ferramentas e scripts usados para fazer o deployment de uma plataforma Mojaloop ao nível de qualidade desejado, desde desenvolvimento, qa ou sandboxes, até pré-produção ou mesmo ampliado para deployments com qualidade de produção. Usa os releases do Mojaloop como núcleo e faz o deployment de todo o conjunto de ferramentas de suporte necessário para correr a Plataforma Mojaloop para um Switch Mojaloop.
* **Kafka** - Esta tecnologia é aproveitada para suportar a exigência do Mojaloop de mensagens de dados de alta velocidade e alto volume, mantendo ao mínimo os nossos requisitos de hardware.
* **JavaScript** - A aplicação Mojaloop está escrita principalmente em JavaScript.
* **Kubectl** - Esta é uma interface de linha de comandos para correr comandos contra clusters Kubernetes.
* **Kubernetes** - Esta ferramenta empresarial fornece uma camada de abstração, gestão de infraestrutura e um sistema de orquestração de contentores.
* **Markdown** – A documentação é um entregável deste projeto, tal como o código, e por isso queremos tratá-la como o código em termos de versionamento, revisão, check in e acompanhamento de alterações. Queremos também que a documentação seja facilmente visualizável online, sem abrir constantemente um visualizador. O GitHub tem um formato integrado chamado Markdown, que resolve bem este problema. Os mesmos ficheiros servem para o Wiki e para os documentos. Podem ser revistos com o check in, usando as mesmas ferramentas, e visualizados diretamente no GitHub. Considerámos Google Docs, Word e PDF, mas estes formatos binários não são facilmente comparáveis por diff. Uma desvantagem é que o markdown permite apenas formatação simples — sem tabelas complexas nem mudanças de tipo de letra — mas isto deve ser suficiente quando o nosso objetivo principal é a clareza.
* **Mojaloop Testing Toolkit (TTK)** – O [Mojaloop Testing Toolkit](https://github.com/mojaloop/ml-testing-toolkit)) é uma ferramenta tipo canivete suíço para atividades relacionadas com o Mojaloop, usada principalmente para testes ponta a ponta, demonstrações, criação de mocks de APIs e em vários outros cenários ampliados. As coleções de teste do Mojaloop usam o ML TTK e esta é a ferramenta de preferência para testes ponta a ponta, estando também integrada nos scripts de teste automatizado (usando a CLI do TTK no IaC e noutros ambientes de dev/qa).
* **MySQLWorkbench** – O [MySQL Workbench](https://www.mysql.com/products/workbench/) é uma ferramenta visual unificada para arquitetos de bases de dados, desenvolvedores e DBAs. O MySQL Workbench fornece modelação de dados, desenvolvimento em SQL e ferramentas de administração abrangentes para configuração do servidor, administração de utilizadores, backup e muito mais. O MySQL Workbench está disponível para Windows, Linux e Mac OS X.
* **NodeJS** - Esta ferramenta de desenvolvimento é um runtime de JavaScript construído sobre o motor JavaScript V8 do Chrome, que corre o Mojaloop. O NodeJS foi concebido para criar microserviços simples e tem um enorme conjunto de bibliotecas open source disponíveis. O desempenho do Node é adequado e, embora os componentes Node não escalem verticalmente em grande medida, planeamos escalar horizontalmente, o que faz bem. O código original do Interledger foi escrito em NodeJS, tal como o protótipo level one. A maioria das equipas já usava Node, pelo que fazia sentido como linguagem. No código NodeJS, usamos o [Standard](https://www.npmjs.com/package/standard) como guia de estilo de código e para impor o estilo de código.
* **NPM** - O NPM é o gestor de pacotes do Mojaloop, dado que JavaScript é a linguagem de programação por omissão.
* **Percona** para **MySQL** - Estas ferramentas são aproveitadas como sistema de gestão de bases de dados relacionais, para assegurar alto desempenho e funcionalidade de nível empresarial para o sistema Mojaloop. Precisávamos de um backend SQL que fosse amigável para open source e que pudesse escalar num ambiente de produção. Assim, escolhemos o MySQL, um sistema de gestão de bases de dados relacionais open source.
* O **Postman** é uma aplicação do Google Chrome para interagir com APIs HTTP. Apresenta uma GUI amigável para construir pedidos e ler respostas.
* **Rancher 2.0** - A gestão, o aprovisionamento e a monitorização da infraestrutura são fornecidos pelo Rancher 2.0, que é uma plataforma empresarial de Kubernetes que gere deployments e clusters Kubernetes, na cloud e on-prem. O Rancher torna fácil às equipas de DevOps testar, fazer o deployment e gerir o sistema Mojaloop, independentemente de onde esteja a correr.
* **Slack** – O Slack é usado para a comunicação interna da equipa. Foi escolhido em grande medida porque várias equipas já o usavam e gostavam dele como abordagem leve, em comparação com o email.
* **SonarCloud** – Precisamos de um dashboard online da qualidade do código \(dimensão, complexidade, problemas e cobertura\) capaz de agregar o código de todos os repositórios. O SonarCloud é gratuito para o Mojaloop, com alguma configuração. Oferece também verificações de qualidade nos Pull Requests e classificações baseadas nas quality gates aplicadas.
* **SourceTree** – O [Sourcetree](https://www.sourcetreeapp.com/) simplifica a forma como interage com os seus repositórios Git, para que se possa concentrar no código. Visualize e gira os seus repositórios através da GUI simples de Git do Sourcetree. Mas fica ao critério do desenvolvedor usar a ferramenta da sua preferência, seguindo as recomendações gerais do GitHub.
* **Visual Studio Code** - O [Visual Studio Code](https://code.visualstudio.com/) é um editor de código redefinido e otimizado para construir e depurar aplicações web e cloud modernas. O Visual Studio Code é gratuito e está disponível na sua plataforma preferida — Linux, macOS e Windows.
* **ZenHub** – Precisávamos de uma solução de gestão de projetos muito leve e baseada na cloud, para suportar equipas distribuídas. Tinha de suportar epics, stories e bugs, e um quadro de projeto básico. Foram consideradas as ofertas online do VS e do Jira. Para uma pequena equipa de desenvolvimento distribuída, um serviço online era melhor. Para um projeto open source, não queríamos custos contínuos de manutenção de um servidor. A integração direta e forte com o GitHub era importante. Era muito útil acompanhar o trabalho de cada microserviço junto desse microserviço. O Jira e o VS têm ambos mais overhead do que o necessário para um projeto desta dimensão e não se integram tão limpidamente com o GitHub como desejaríamos. O ZenHub permitiu-nos começar a trabalhar imediatamente. Uma desvantagem é a falta de suporte para diagramas de fluxo cumulativo e de suporte para acompanhar o \# de stories em vez de pontos, pelo que fazemos isto manualmente, com uma folha de cálculo atualizada diariamente e os resultados publicados no canal Slack "Project Management".

**ESCOLHAS DE TECNOLOGIA**

* **Desenvolvimento agile** - Esta metodologia é usada para acompanhar e conduzir o projeto. Os requisitos precisam de ser refinados à medida que o projeto é desenvolvido, pelo que escolhemos o desenvolvimento agile em vez de waterfall ou lean.
* **APIs** - Para evitar confusão decorrente de demasiados microserviços em mudança, usamos APIs fortemente definidas, conformes ao nosso padrão de desenho [Pragmatic REST](pragmatic-rest.md). As APIs serão definidas usando OpenAPI. As equipas documentam as suas APIs com Swagger v2.0 ou RAML v0.8, para poderem testar, documentar e partilhar automaticamente o seu trabalho. O Swagger é ligeiramente preferido, dado existirem ferramentas gratuitas. O Mule fará uso do RAML 0.8. O Swagger pode ser convertido automaticamente para RAML v0.8, ou manualmente para RAML v1.0, se se desejar legibilidade adicional.
* **Testes automatizados** - Em grande parte, a maioria dos testes será automatizada, para permitir testes de regressão fáceis. Consulte a [estratégia de testes automatizados](automated-testing.md) e as [métricas de qualidade do código](code-quality-metrics.md) para as normas.
* **Alojamento** - O Mojaloop foi concebido para ser agnóstico quanto à infraestrutura e, como tal, é suportado por instalações AWS, Azure e On-Premise.
* **Interledger** – O Mojaloop precisava de um protocolo de transporte de fundos leve, aberto e seguro. O [Interledger.org](http://Interledger.org) fornece tudo isso. Fornece também a capacidade de ligação a outros sistemas. Considerámos também sistemas de block chain, mas os sistemas de block chain enviam mensagens muito grandes, cuja entrega será mais difícil de garantir na infraestrutura do terceiro mundo. Além disso, embora os sistemas de blockchain proporcionem bom anonimato, esse não é um objetivo do projeto. Para permitir a deteção de fraude, as autoridades reguladoras precisam de poder solicitar registos de transferências por conta e por pessoa.
* **Open source** - Todo o projeto foi lançado como open source, de acordo com os [princípios do Level One Project](https://leveloneproject.org/wp-content/uploads/2016/03/L1P_Level-One-Principles-and-Perspective.pdf). Todas as ferramentas e processos têm de ser amigáveis para open source e suportar projetos que usem uma licença Apache 2.0, sem requisitos de licenças restritivas para os desenvolvedores.
* **Sistema operativo** – O Microsoft Windows é amplamente utilizado em muitos países-alvo, mas precisamos de um sistema operativo livre de taxas de licenciamento e compatível com open source. Estamos a usar Linux. Não temos dependência da distribuição em particular, mas estamos a usar o Amazon Linux básico. Nos contentores Docker é usado o [Alpine Linux](https://alpinelinux.org/).
* **Microserviços** - Porque a arquitetura precisa de fazer deployment e escalar com facilidade, e de ter componentes facilmente substituíveis ou atualizáveis, será construída como um conjunto de microserviços.
* **Scaled Agile Framework** - Existiam quatro equipas de desenvolvimento iniciais, geograficamente separadas. Para manter a fase inicial do projeto em rumo, foi escolhido o [scaled agile framework \(SAFe\)](https://www.scaledagileframework.com/). Isto significa que o trabalho é dividido em program increments \(PI\), que têm normalmente a duração de quatro sprints de 2 semanas. Tal como nos sprints, o PI tem objetivos demonstráveis definidos em cada reunião de PI.
* **Serviços** - Os microserviços são agrupados e colocados em deployment em alguns serviços, tais como o DFSP, o Central Directory, etc. Cada um destes terá interfaces definidas simples, scripts de configuração, testes e documentação.
* **Modelação de ameaças, modelação de resiliência e modelação de saúde** - Dado que o código do Mojaloop precisa de trocar dinheiro num ambiente com infraestrutura muito instável, tem de ter boa segurança e resiliência, e de reportar facilmente o seu estado de saúde e tentar automaticamente regressar a ele. 
* **USSD** - Os smartphones representam apenas 25% do mercado-alvo e não são atualmente suportados pela maioria dos serviços de transferência de dinheiro, pelo que precisamos de um protocolo que funcione em feature phones simples. Tal como o M-Pesa, usamos USSD entre o telefone e o prestador de serviços financeiros digitais \(DFSP\).
